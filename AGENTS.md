# GHUB-X (crate `ghubx`)

G HUB-style control app for the Logitech G502 HERO (USB `046D:C08B`), Rust + egui 0.37.

## Commands

- Build: `cargo build` (debug) / `cargo build --release` (no console window, thin LTO)
- Tests: `cargo test` (164 tests, about 5 s: protocol decoding, palette, OSD render, game scan parsers, export/import, Lua worker, and engine behaviour through a fake input sink and device channel; nothing touches the mouse or injects input)
- Lint: `cargo clippy --all-targets` (keep it warning-free)
- Device probe (read-only): `cargo run --bin probe`
- Probe subcommands: `probe ghub-status` (is `lghub_agent.exe` running), `probe ghub-close` / `probe ghub-start` (same `win.rs` calls as the UI buttons), `probe takeover-test` (WRITES to the mouse: host mode, spy map, DPI, rate, LEDs, then releases to onboard; exit 2 if G HUB's agent or any `ghubx.exe` is running, 0 only if every step passes), `probe release` (WRITES: stop spy, identity map, onboard mode; exit 2 if G HUB's agent is running)
- `probe listen [secs]` (read-only): prints 0x8110 button events, also next to a running GHUB-X or G HUB
- Env `GHUBX_CONFIG_DIR`: base dir instead of `%APPDATA%` (config is `<dir>\ghubx\config.toml`); point `--shot` runs at a frozen copy so live config changes can't alter screenshots
- Shot flags (in memory only): `--theme <id>`, `--accent <RRGGBB>`, `--follow-lighting`, `--switch-to <id>` (switches theme on frame 10 via the same path as the Appearance tiles)
- `probe osd-png <out.png> dpi <value> <levels> <active> | profile <name> [--theme id] [--scale f]` writes the OSD as a PNG; `probe osd dpi <value> <levels> <active> | profile <name>` shows it on screen for ~2 s
- `probe export-theme <idx> <file>` / `probe import-theme <file>` (custom themes as `.ghubxtheme`; never writes the config)
- WRITE probes (each exits 2 while `lghub_agent.exe` or any `ghubx.exe` runs): `probe onboard-save <slot 1..5> <app> <profile> [--dry-run] [--activate]` (`--dry-run` prints the encoded sector and `not_stored` and never opens the device), `probe onboard-restore <slot|all>` (copies the ROM profile), `probe onboard-activate <slot>`, `probe dpi-led <on|off>`, `probe startup-effect <on|off>`; `probe onboard-backup <dir>` is read-only
- `probe obs-status` / `probe obs <action> [target]` (OBS WebSocket; never prints the password; run only with a real OBS)
- `probe fx-screen-check` (read-only: sampled vs exact 1:1 average of Full and Center, exit 1 if the best of three rounds is off by more than 6; the sampler captures into a 320 x 180 bitmap because a coarser grid aliases with text)
- `probe fx-sample <x0> <y0> <x1> <y1>` (read-only: same check for an own rectangle in thousandths of the screen, three rounds, plus the average of the same rectangle from `fx::screen_picture`)
- `probe fx-screen [secs]` / `probe fx-audio [secs]` (read-only, no HID: raw screen samples and capture timing; audio peak/bass plus a line when the loopback client opens or closes)
- `probe game-sens` (read-only: CS2 / Valorant sensitivity and half-turn counts)
- `probe onboard` (READ-ONLY dump of the mouse's on-board profile directory; refuses while G HUB runs)
- `probe cache-sync` (writes the saved copy), `probe export-app <idx> <file>` / `probe import-app <file>` (never writes the config), `probe ghub-autostart` (read-only), `probe save-dialog`
- `probe games` lists installed games (name | source | folder | G HUB id | commands with a key combo); `probe pick-exe` opens the native exe picker and prints the result
- Scripted UI: `ghubx.exe --dev --script <file>` (needs `GHUBX_CONFIG_DIR`; exit 2 otherwise, exit 3 on a malformed line) runs the real UI off-screen at (-32000,-32000) with synthetic egui input, one script line per frame, no tray/mutex/sync. Commands: `wait <ms>`, `move x y`, `click x y`, `rclick x y`, `dclick x y`, `drag x1 y1 x2 y2`, `scroll x y dy`, `key <EguiKeyName>`, `text <string>`, `shot <png>`, `quit` (normal exit, config saved). Observer mode never installs the wheel hook or enables scroll acceleration. `python tools/ui_test.py [name ...]` runs 45 click scenarios (each starts from `tools/ui_seed_config.toml` in a fresh folder under `%TEMP%\ghubx_ui_test`, asserts on the saved config / pixels); a full run takes 4 to 6 minutes (3 to 40 s per scenario, longer on a busy machine). Coordinates assume a 1024x768 window at 100% scale. `add_detected_game` and `use_game_sensitivity` need this PC's Counter-Strike 2 install and its sensitivity of 0.51
- Dev instance: `ghubx.exe --dev` needs `GHUBX_CONFIG_DIR` (else exit 2), uses mutex `Local\GHUBX-single-instance-dev`, tray class `GHUBX_TRAY_DEV`, tooltip "GHUB-X (dev)"; `engine::set_observer(true)` (set for `--dev` and `--shot`) means it never takes control, never closes/starts G HUB and never writes the on-board slot; autostart toggles are disabled. Safe to run next to the live app for scripted tests
- Flags: `--minimized` (start hidden in the tray), `--shot <page> <out.png>` (no mutex, no tray)
- Regression check for any UI change: `python tools/shots.py render <dir>` before and after (all 50 pages from `tools/ui_seed_config.toml`; two renders of the same code are pixel-identical), then `python tools/shots.py diff <before> <after> 0`: only the pages you meant to change may differ. Add `--theme <id>` to render another theme. New `--shot` pages must be added to `PAGES` in `tools/shots.py`.
- Page screenshots without touching the mouse: `target/debug/ghubx.exe --shot <page> <out.png>`
  pages: home, dropdown, assign, assign2, gshift, select, keys, actions, macro, macroname / macrotype / macroseq / macroedit / macrorec / macromenu / macrocustom / macrofold / macroconfirm / macroaction (the full-screen macro editor in each state), p180warn (Perfect 180 box with the implausible-travel warning), obsactions / obsnew (ACTIONS with the OBS section open / its CREATE NEW ACTION form), sens, light, fixed, effectmenu (LIGHTSYNC with the EFFECT menu open), screenfx, screenfxmine (SCREEN SAMPLER panel with three own samples, the second in use), sampleedit (the full-window "Edit Samples" overlay with three samples, the second selected), audiofx, audiofxadv (host-driven effect panels), devset, wdl (LIGHTSYNC with Windows Settings ON), slotmenu / slotconfirm / slotdetails (Device Settings on-board slot menu, confirmation bar, details), profiles, appdetail, scriptedit (the full-window Lua script editor with the seeded template), settings, sleep (settings with lighting sleep on), appearance, themeedit (theme editor open on a sample draft), mythemes (two sample custom themes), p180game (ACTIONS with the Perfect 180 game-sensitivity line), onboard (Device Settings with sample on-board slots), ghub (Settings > G HUB tab), addgame (Profiles with the add form open), gamecmds (Assignments > COMMANDS for an in-memory Counter-Strike 2 app), diag
- Rebuilding the release while the app runs (it usually controls the user's mouse): rename `target/release/ghubx.exe` to `ghubx.old.exe` (Windows allows renaming a running exe), `cargo build --release`, post `WM_APP+3` to the `GHUBX_TRAY` window (clean quit: the mouse goes back to on-board mode), start the new exe (add `--minimized` if the old window was hidden), check with `probe` that mode is 2 again, delete `ghubx.old.exe`. About 0.5 s without control.
- Never `taskkill /F` a controlling instance: the mouse stays in host mode with its remapped buttons muted. If that happens, `probe release` puts it back in on-board mode.

## Layout

- `src/hidpp.rs` HID++ 2.0 transport (short 0x10 on usage 0x0001, long 0x11 + all input on usage 0x0002)
- `src/device.rs` G502 operations (DPI 0x2201, report rate 0x8060 in ms, onboard 0x8100, LEDs 0x8070, button spy 0x8110)
- `src/profile.rs` data model (apps -> profiles -> base/G-Shift layers, DPI table, lighting, macros) + onboard sector CRC
- `src/engine.rs` takeover policy (only when G HUB's `lghub_agent.exe` isn't running), spy bitmap -> actions
- `src/io.rs` HID owner thread; `src/win.rs` SendInput, foreground app, G HUB process control, autostart, wheel hook
- Tray / background (`win.rs`, pure Win32): hidden top-level window (`WS_EX_TOOLWINDOW | WS_POPUP`, never shown, so it receives `TaskbarCreated` and `WM_ENDSESSION` broadcasts) of class `GHUBX_TRAY` on its own thread; `WM_ENDSESSION` (wParam != 0) runs the quit path so a shutdown/logoff releases the mouse; mutex `Local\GHUBX-single-instance` (a second launch finds the tray window with `FindWindowW` (not message-only), posts `WM_APP+2` and exits). Messages: `WM_APP+1` tray callback (left click/double click show, right click menu Open/Quit), `WM_APP+2` show main window, `WM_APP+3` quit. Show/hide use raw `ShowWindow` (eframe runs no frames while hidden, so the engine/IO threads must never depend on the UI loop; `ui::spawn_stash` keeps the UiEvent channel drained while hidden). Shutdown is one function, `ui::Exit::run` (save config, engine Quit, wait IO thread, remove icon), used by `on_exit` and tray Quit. `win::tray_ready()` gates close-to-tray and `--minimized` hiding (no tray = window stays reachable). `--minimized` starts the window at (-32000,-32000), hides it after eframe's first frame and re-centres it on the work area. One icon: `win::app_icon_rgba(size)` (tray 32, window 64). Control watchdog: the IO thread's periodic refresh sends `EngineMsg::ControlLost` if the mouse left host mode while controlled; the engine retries after 1 s. Config: `general.close_to_tray` (default on), `general.start_minimized` (adds ` --minimized` to the autostart Run entry)
- `src/ghub_import.rs` imports `%LOCALAPPDATA%\LGHUB\settings.db` (copied to temp first)
- OSD (`src/osd.rs`): `render(kind, palette, scale)` is pure CPU (ab_glyph, premultiplied BGRA); `show(kind)` drives a layered, click-through, topmost, no-activate window (`GHUBX_OSD`) on its own thread (fade 100 ms, hold 1400, fade 300; monitor of the foreground window, DPI scaled). The engine calls it (`Engine.osd`) for DPI buttons and for profile changes while in control (`general.osd_dpi`, `general.osd_profile`). `general.dpi_flash` flashes both zones in `dpi_flash_color(level)` for 1.2 s (`flash_until`, `expire_flash`). Engine tests use `Engine.persist = false` and an injected `osd` closure; `set_observer` is a process-wide flag so engine tests run serially
- Reading on-board profiles: `DevCmd::ReadOnboard` walks sector 0 and each directory sector one per IO pass (`io::OnboardJob`), results come back as `UiEvent::Onboard`; Device Settings shows the slot rows from them. The read path never calls `write_sector`; writing is described under 'On-board memory writes'
- Macros: `Macro` has up to three step lists (`steps`; for `MacroKind::Sequence` ON PRESS, plus `hold` = WHILE HOLDING and `release` = ON RELEASE), `std_delay` (USE STANDARD DELAYS; `standard_delay()` infers it for older macros), `show_up_down`, `color`. A `MacroStep` is a key event, a pause, or has `act: StepAct` (`Text` to type, `Do(Assignment)` to run a SYSTEM command / launch; `step_allowed`). `engine::Player` plays them (`play` for the repeating kinds, `play_sequence`: press once, hold looped until release unless the button was already released, release once, keys left down stay down across sections and are released at the end). `Do` steps that need the engine (System, Perfect 180, scroll accel) go back as `EngineMsg::Tap` over the loopback sender (`with_loopback`). `Input` has `text` / `launch` (`win::type_text`, `win::launch` via ShellExecute). `EngineMsg::TestMacro` carries the whole macro and is NOT played in observer mode (`--dev`, `--shot`). The importer picks the type from G HUB's `useRepeatActions` / `useSimpleActions` / `useToggleActions` flags
- OBS actions (`src/obs.rs`): `Assignment::Obs(ObsAction)` on a button or as a macro step (`Tap` -> `Engine.obs`) is sent to OBS Studio's WebSocket server (obs-websocket v5, 127.0.0.1) by one worker thread (`obs::Handle`: lazy connect on the first command or `refresh()`, socket dropped on any error, no polling). The port and password are read from OBS's own `%APPDATA%\obs-studio\plugin_config\obs-websocket\config.json` at every connect: GHUB-X never stores or logs the password. In observer mode (`--dev`, `--shot`) the handle is `Handle::fixed(NotRunning)` and nothing connects. The user's own actions with a target are in `Config.obs_actions`; the ACTIONS tab's OBS section starts collapsed and refreshes the lists when expanded (at most every 5 s). Tests use an in-process tungstenite server on 127.0.0.1:0, never a real OBS
- Lua scripts (`src/lua.rs`): `Profile.script` holds an `OnEvent(event, arg)` script with G HUB's API names (PressKey, PressMouseButton, Sleep, OutputLogMessage, IsKeyPressed, EnablePrimaryMouseButtonEvents, PlayMacro...). `mlua::Lua` is `!Send`, so one worker thread (`lua::Handle`, same pattern as `obs::Handle`) owns the state and every `SendInput` goes through `engine::Input`; the engine pushes `LuaMsg::Script` when the active profile's script changes and `LuaMsg::Event` for every spy-bitmap change (slots 0/1/2 -> MOUSE_BUTTON 1/3/2, others G1..G11; MOUSE_BUTTON events are dropped unless the script enabled them). `Script("")`/`Stop` tear the state down (PROFILE_DEACTIVATED first), a load error or runtime error lands on the 200-line console the editor shows, and an instruction hook (~20M instructions/event) kills runaway scripts. **Lua scripts only run while GHUB-X controls the mouse**; `--dev`/`--shot`/scripted runs use `Handle::fixed()` and never create a state. Editing happens in the full-window `src/ui/lua_editor.rs` overlay opened from Profiles -> app detail -> SCRIPTING (`GhubApp::script_editor`, `script_overlay`); the script is saved with the app in `.ghubx` exports and reported as not storable by `encode_onboard`
- Macro editor (G HUB's full-screen one): `src/ui/macros.rs` draws the overlay with three stages (name, type tiles, editor with sections, chips, the "+" menu, recording, options column, RESET / SAVE, confirmations); `src/ui/macros_model.rs` is its pure model (kind switching, items / chips with fold of key down+up, delete, move, copy / paste, save normalisation, key-balance warnings) and holds the unit tests. While `asg.editor` is `Some`, `GhubApp::ui` draws the overlay instead of the route. Entry points: CREATE NEW MACRO (name stage), EDIT in the list and 'Edit macro' in the slot menu. No scenario may press TEST MACRO (it types) or the chooser's CREATE NEW (native dialog)
- Host-driven lighting (`src/fx.rs`): SCREEN SAMPLER and AUDIO VISUALIZER (`Effect::Screen` / `Effect::Audio`, settings in `Lighting.host: HostFx`) cannot run on the mouse, so a thread (`fx::Handle`, 50 ms tick, screen capture at most every 100 ms) computes the colour and puts it in a `Mailbox`; the IO thread takes it only while it holds host control and writes it as a fixed colour with `set_zone_effect(.., false)`. RAM ONLY, never flash: a host-driven path must never pass `true` (15 writes a second would wear the flash out). The screen sampler's area (`ScreenArea`) can be the full screen, one of nine fixed grid cells, or an own `Rect` (thousandths) that matches a named `Config.samples` entry; samples are edited in the full-window "Edit Samples" overlay opened from the panel's EDIT button, `Config::set_sample_rect` keeps zones that use a sample following every move/resize, and removing a sample puts its zones back on `Full`. The engine tells the thread which zones it drives (`Engine.fx`, `Applied.host`), calls it with `[None, None]` before anything that ends control or flashes, and re-sends a zone's device effect when it stops being host-driven. `DevCmd::Yield` clears IO's `controlled` flag when G HUB takes over. Audio: `win_source()` reads the endpoint meter first and keeps the WASAPI loopback client open only while something plays (closed after 3 s of silence, and `Source::release` when the effect is no longer needed) so GHUB-X never keeps Windows awake. `--shot` has no fx thread (fixed fallback colours). Preview: `Handle::preview_zone` per zone, forgotten after 500 ms
- On-board memory writes (`onboard_write.rs`, the ONLY writer, used by the IO thread and the probes): refuse while G HUB runs, sector outside 0..=5 or bad CRC; back up sectors 0..=5 (each read twice) to `<config dir>\onboard_backup\<timestamp>`; write only sectors that differ, read back and compare, retry once, then write the backup bytes back; afterwards the engine gets `Reapply` because a sector write makes the mouse reload its stored profile (DPI and LEDs jump). `profile::encode_onboard` is byte-exact to what G HUB writes (golden test against `tests/fixtures`); macros, launch, Perfect 180 etc. are not storable (`not_stored`), a `Default` G-Shift slot inherits the base slot. Device Settings never writes on the first click: the slot menu builds a pending action, the bottom bar's WRITE TO MOUSE sends it. A `Default` G-Shift slot also acts as the base assignment in the engine
- DPI LEDs and startup effect (Device Settings): `general.dpi_led_always_on` (0x1300 NV config + level via setLedState while controlling), `DeviceState.startup_effect` (0x8070 fn4/fn5)
- Windows Dynamic Lighting (`win::wdl_state` / `set_wdl`, registry value `AmbientLightingEnabled` of the `HID_DEVICE_SYSTEM_VHF` device key; in-memory in `--dev` / `--shot`): while ON the engine sends no lighting (`Applied.send_leds`), LIGHTSYNC shows the switch and an inert, dimmed panel
- Engine input goes through `engine::Input` (`RealInput` forwards to `win::*`; tests inject a recorder), so button behaviour is unit-tested without touching the mouse
- Saved copy: `assets::sync_cache()` (background thread at startup of the app and `--dev`, never `--shot`) copies G HUB's fonts, device images, metadata and `applications.json` to `%LOCALAPPDATA%\ghubx\cache` (`GHUBX_CACHE_DIR` overrides). Loaders try the install first, then the copy; `GHUBX_NO_GHUB=1` pretends G HUB is not installed. Diagnostics shows each source (`assets::source`). Settings > G HUB also has the 'Start G HUB with Windows' row (`win::startup_approved` / `set_startup_approved`, StartupApproved\Run)
- Export/import: `profile::export_app` / `import_app` (`.ghubx` = TOML, `format = 1`), `Config::add_imported`; dialogs `win::pick_file` / `save_file`
- Game sensitivity (`games::game_sensitivity`): reads CS2's `cs2_user_convars_0_slot0.vcfg` and Valorant's `RiotUserSettings.ini` (read-only, newest file) to calibrate Perfect 180 (`180 / (yaw x sens)`); used when adding a detected game and by the 'USE MY ... SENSITIVITY' line in the Perfect 180 box. `--shot` uses a fixed sample, never the real files
- Games (`src/games.rs`): G HUB's `applications.json` is read at runtime (`games::preload()` at startup, `db()` / `db_blocking()`), never copied into the repo. `scan()` finds installed games (Steam acf, Epic items, Riot yaml, registry rules, GOG, Ubisoft; the last three are unit-tested only). `AppEntry.dir` (install folder) matches the foreground *process path* (`win::foreground_path`, `Status.foreground_path`); an `exe` match beats a `dir` match, the longest `dir` wins. `AppEntry.ghub_id` adds the game's commands (as `Assignment::Shortcut`) to Assignments > COMMANDS. Profiles > ADD GAMES & APPS lists detected games and has BROWSE (`win::pick_exe`, `GetOpenFileNameW`)
- Perfect 180: presets `P180_GAMES` (indices 0..=3 are stable; `P180_CUSTOM` = 3, shown last via `P180_ORDER`), `Extras.p180_angle`, per-profile `Profile.turn: Option<TurnCal>` (`turn_for`, `turn_counts`). The box's HARDWARE FLICK section sets `dpi.shift` so a physical swipe = 180 deg (`flick_dpi`, `set_flick_dpi` keeps the value in the stage list because on-board shift is a stage index); with a `System(DpiShift)` button saved to a slot the flick runs on the mouse itself
- `--shot` runs ignore live spy button events (the live app's presses would leak into screenshots) and the shot clock advances 0.05 s/frame once the page is ready so popups finish fading in
- Themes: `src/ui/palette.rs` holds `Palette` (global `pal()` / `set_palette`), 5 presets (ids `ghub-dark`, `ghub-light`, `razer-green`, `midnight`, `ember`; `ghub-dark` is the original G HUB look verbatim), `n(level)` neutral ramp, `ink(alpha)`, `with_accent`, `resolve(&Appearance, lighting_accent)`. No `Color32` literals in `src/ui` except images/renders, the colour picker, LEDs, posters, shadows and the close-button red. `App::ui` recomputes the palette every frame (config `[appearance] theme/accent/follow_lighting`; follow-lighting uses the logo zone) and restyles when it changes. Settings > Appearance is tab 1. User-made themes: `Appearance.custom: Vec<CustomTheme>` (bg / surface / text / accent; `Appearance.theme` may hold a `custom-...` id), `palette::custom_palette` derives everything else, `palette::contrast` gives the WCAG ratio; MY THEMES tiles, IMPORT/EXPORT/EDIT and the editor (live preview: the whole window uses the draft palette while it is open; it is dropped whenever the route leaves Appearance) live in `src/ui/themes.rs`; the colour picker in `light.rs` takes its state (`PickerState`) as a parameter
- `src/ui/` G HUB look: fonts from `C:\Program Files\LGHUB\resources\app.asar`, renders + hotspots from `C:\ProgramData\LGHUB\depots\*\g502_hero`

## Rules

- Never write spy map / host mode while G HUB is running (it owns the mouse); `--shot` forces `take_control = false`.
- Don't ship Logitech assets; they are read from the local G HUB install at runtime.
- `write_sector` (flash) is called from `onboard_write.rs` only (backup, verify, roll back). Checked on this mouse on 2026-11-22: a test write to slot 5 was restored byte-identical, then the Desktop profile was written to slot 1.
- Config: `%APPDATA%\ghubx\config.toml`.
- Live check with G HUB closed: `probe ghub-close`, then `probe takeover-test` (all 8 steps passed on 2026-11-21). `probe release` is the rescue command (mouse back to onboard mode). Since 2026-11-22 the active on-board slot is 1 and holds the Desktop profile (600 DPI), so the pointer keeps its speed when no software controls it; the factory sectors are saved in `%APPDATA%\ghubx\onboard_backup`.
